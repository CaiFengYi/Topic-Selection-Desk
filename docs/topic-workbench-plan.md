# 本地选题台首版实施方案

日期：2026-10-27。本文是待实现方案，依据PROJECT_CONTEXT.md第12节的用户决定。终端验证已存在；页面与下述新增能力尚未实现。

正式规格已发布至[本地任务跟踪器](../.scratch/topic-workbench/PRD.md)。用户补充的实施顺序为：先建立前端原型并确认接口，再对接真实服务，主要测试从前端操作进行。

## 首版交付目标

在本机浏览器中完成：选择或添加热点 → 研究并展示背景、材料和关键词 → 直接推荐或人工选词推荐 → 修改、换一批及选用多个草稿 → 关闭后重新打开仍可读取。

不要求先证实输入标题中的所有说法。研究来源归属、材料缺口和待查证知识必须保留；既有内存例仍是研究证据不足，不能宣称三例最终验收全部通过。

## 已确认的产品规则

1. 两种入口：从B站、抖音、微博本地榜单点选；手动输入标题或描述，可选附链接、时间、地点及关注点。
2. 事件定位不清时暂停提词，展示已有候选或请用户补充；同一事件内部的说法分歧不因此阻断研究。
3. 自动取材限公开搜索与网页正文；用户可补充评论、字幕片段及梗的解释，明确来源是用户提供。自动评论与字幕取材留待后续。
4. 材料过少只警告，保留已有材料和错误，不补查、不重读、不自动重试，也不付费诊断原因。警告不等于材料已经通过验收。
5. 提词后停止，等待用户点击默认“直接推荐”或“我来挑关键词”。人工模式仅使用本轮选中词，不强行组合全部词。
6. 用户可以修正词义解释；原词、引用与原AI解释保留，修正单独保存并用于后续推荐。修改本身不收费。
7. 每批最多三个候选，允许更少或没有；标题、开场保留有依据的原物件和数字，形成独立知识问题。
8. “换一批”是用户明确触发的新模型请求，复用材料和当前关键词，尽量避开已有角度，保留历史与人工修改，明示计费并受预算约束。
9. 同一热点可选用多个候选，分别保存状态。选用不启动知识核验、脚本或视频生成。

## 实现方式建议

### 本地界面与服务

- 第一阶段先提供可点击的前端原型，使用明确标注的模拟数据和接口响应，不调用付费服务、不改正式账本。通过原型确认交互与候选接口契约后，再接入本地服务；不先实现完整后端再交付页面。
- 在工作区新增独立的topic_workbench模块与启动入口，复用TrendRadar环境。保持原版静态报告和终端验证入口可用。
- 使用当前锁定环境已有的Starlette、Uvicorn及轻量HTML/CSS/JavaScript；首版不新增前端构建链。服务仅监听本机回环地址。
- 页面分为榜单、热点研究和选题草稿三个区域。平台、排名、来源链接和采集时间从本地数据读取；采集时间与事件时间分开呈现。
- 新入口中的榜单刷新仅采集与保存，不调用原版整榜AI分析；AI操作仍由人选定热点后触发。沿用首轮不建立定时任务的边界。
- 研究和推荐在后台执行，页面展示正在执行的阶段和错误。首版串行执行付费任务，避免重复点击创建重复请求；中断后保留材料、调用记录和费用预留。

### 数据与接口

- 榜单读取既有SQLite；研究、材料、选词、词义修正、推荐轮次和草稿沿用可检查的JSON落盘及原子写入，不先增加另一套数据库。
- 新热点使用独立标识，脱离brakes/fire/memory固定枚举；三个旧案例仍可读取并回归验证。
- 接口围绕读取榜单、创建热点、提交补充说明、启动研究、保存词义修正和本轮选词、生成推荐、换一批、保存草稿与选用状态组织。不向浏览器发送密钥。
- 原始研究结果与用户修正分开，推荐轮次记录当时采用的词和解释；后续修改不改写旧轮次。
- 同输入的结果查看、页面刷新和恢复沿用缓存；显式“换一批”新增轮次身份，不复用旧结果冒充新生成。
- 相同事件的跨平台自动语义合并不作为首版依赖。保留来源信息，不因标题相似就自动混合材料。

### 复用与兼容

- 复用research_validation中的Exa、DeepSeek接入、脱敏、引用检查、预算账本和缓存能力，按需做小范围抽取，避免复制整套客户端。
- 将固定案例的查询与身份、比较条件从通用研究流程中分离，旧案例仍保留原有验证要求。新增事件不能借用内存专用判定来代表普遍研究充分性。
- 为人工补充材料保留准确文本、来源说明及未回查状态；不会把搜索摘要、读取失败页面或用户提供内容伪装成已读取的原网页。
- 修正旧补词自动进入所有推荐的问题；人工推荐所用词以当前选择为准。
- 材料数量、引用有效性、来源说法、编辑质量和用户选用是不同维度。来源数量告警不能替代逐字引用检查，结构通过也不代表事实或科学结论已证实。

### 调用和费用

- 所有新增付费操作继续计入现有validation-output/ledger.json，不另建空账本绕开原累计5元上限；已计账与失败预留不清零。
- 原验证每例至多两次搜索、每次五条结果及一个至多五页正文批次的边界不因增加页面自动放宽。
- 页面查看、保存、词义修正和选用只做本地操作；不额外请求模型来判断是否需要补查或解释已知错误。
- 沿用无隐式重试及请求前费用预留。价格快照失效、预算不足或账号不可用时不发起新付费调用，已有结果仍可查看。
- 本方案不授权增加预算、开定时采集、发送外部通知或发布内容。

## 实施顺序与验证

| 步骤 | 实现 | 验证 |
| --- | --- | --- |
| 1 | 先建立前端原型，模拟榜单、研究卡、关键词、推荐与草稿 | 从前端操作两种入口、两种推荐、词义修改、换一批和多选，演示澄清、警告与失败；不调用API或修改正式账本 |
| 2 | 依据原型确认接口契约 | 对照页面动作明确请求响应字段、任务与结果身份、状态、警告、错误及防重复语义，形成响应样例；记录用户对原型和接口的确认 |
| 3 | 按契约接入通用研究、本地榜单、费用控制与持久化 | 原29项测试保持通过；新增必要行为测试验证任意热点、词义修正、本轮选词、新轮次及多选，刷新不运行整榜AI |
| 4 | 从前端联调、测试与重启恢复 | 连接真实本地服务及临时存储，模拟外部付费服务；页面验证正常和失败路径、缓存及恢复，配合预算、锁和重试专项检查 |
| 5 | 从前端完成真实端到端验证与交付 | 在有效核价及现有预算内验证一个未预置热点，逐项记录成功、失败、用量与告警；不因材料不足补查，不能完成时保留结果并列缺口 |

真实验证不以查明所有争议为通过条件，但不得把取材失败、模型失败或内容未核验称作已经完成。内存倒挂事实缺口继续保留。

原型交互通过不等于真实接口、持久化或预算已验证；主要验收入口在前端，不取消已有后端边界检查。

## 首版完成标准

- 不再依赖三个固定案例才能使用，榜单与手动热点都能进入同一流程。
- 研究完成后等待用户动作；人工材料、词义修正、本轮选词与历史结果可追溯。
- 材料过少有明确警告；可引用文本缺失时如实标明未完成，不伪造背景、关键词或出处，不另行补查。
- 两种推荐、显式换一批、标题与开场编辑、同热点多选及重启读取均可操作；不触发后续视频制作。
- 页面操作与费用记录相符，日志和浏览器数据无密钥泄漏，原入口与既有结果保持可读取。

实施细节可在代码检查中调整；改变已确认产品行为或增加费用上限时需另行讨论。首版不含知识核验流程、脚本、视频生成、发布、自动评论字幕采集及定时采集。
